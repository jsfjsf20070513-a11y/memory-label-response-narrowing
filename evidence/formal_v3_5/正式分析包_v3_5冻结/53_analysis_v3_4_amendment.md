# 正式分析 v3.4：任务 ID 进入必填 Schema

## 失败与判断

v3.3 的 M1 五批共 144 条全部有效并完整合并；M2 第一批两次均无效。第一次集合缺/
多列表为空但长度不唯一，说明有重复 ID；第二次明确少一条。每批 30 条已经不算超大，
继续缩批只能降低而不能消灭抄 ID 风险。

## 唯一运输改动

剩余每批的固定任务 ID 直接写入该批 JSON Schema：`items` 是
`additionalProperties=false` 的对象，全部任务 ID 同时出现在 `properties` 与
`required`。每个值仍只有原来的 `supported:boolean` 和 `reason:string`。

模型不再输出 `task_id` 字符串；程序按冻结任务序列把键值转回旧列表，随后使用原
`validate_review()` 校验完整任务全集。`51_build_review_schemas.py` 生成 25 份静态
Schema，并在每次包核验中机械重建比对。

## 复用与预算

M1 是失败前完整结束的整槽，五份 raw、prompt、chunk 和 merged 可逐字重建，因此整槽
复用。M2 两份无效 raw 只锁定失败史，不进入结果。新跑五名×五批=25 次，8 次重试
余量，总上限 33；v3.2+v3.3+v3.4 最坏累计 76。

## 限制

M1 使用数组运输，其余槽使用键固定运输，存在实现不对称；任务内容和判断标准相同，
但必须报告。此修订发生在编码后且经历多次运输失败，最终结果只能视作当前材料上的
探索性正式检验，强确认依赖全新回答复制。
