# 正式分析 v3.1：Codex 菜单方向分表

## v3 在哪里停了

v3 的六槽长合成校准全部首试通过。正式阶段中，M1 与 M2 各 8 个盲化编码
单元全部首试有效；M3 的第一个单元也有效。第二个 M3 单元
`ENCODE_V3_M3_S2_C02` 两次都返回了结构合法的 JSON，但 Codex 把菜单内方向
的 `menu_id` 与本应为 null 的 `name/definition` 同时填了。语义校验两次都拦下，
v3 按冻结规则停止。

当时运行状态为 25 次尝试：6 校准 + 17 个有效正式 raw + 2 个已完成的无效 raw。
无 `manifest_coding.json`、无解盲、无汇总、无人工改票。

## 为什么不再靠提示词重试

v3 的提示已明写：菜单内方向填 `menu_id` 时，`name=null` 且 `definition=null`。
Codex 在同一单元连续两次违反，说明“继续叮嘱”不是稳定解。v3.1 不再让 Codex
面对这个可填错的组合。

## v3.1 的分表运输

M3 的每份回答改为两个数组：

- `menu_directions`：只有 `local_id/menu_id/evidence_span_id/tag`，Schema 中根本没有
  `name` 和 `definition`；
- `extra_directions`：只有 `local_id/name/definition/evidence_span_id/tag`，Schema 中根本
  没有 `menu_id`。

程序按共用的 `local_id` 将两张表合并，然后回到 v3 的统一内部运输格式，
再走原有片段取回、规范 Schema、复核和统计。菜单、方向边界、数学/非数学标签、
判决、模型、强度和统计全部不变。M1/M2 与开放组仍用 v3 格式。

## 复用 M1/M2 的决定

v3.1 不重跑 M1/M2 的 16 个有效单元，也不复用那个孤立的 M3 有效单元。理由是：

1. M1/M2 都在失败发生前完整结束，形成六份完整规范编码，是干净的整槽边界；
2. v3.1 不改 Claude 菜单运输或任何判决尺子，重跑只会增加随机票和 token 支出；
3. 执行方没有解盲或查看臂差异，停止原因与研究结果无关；
4. 孤立 M3 单元不复用，新分表格式下 M3 整槽 8 个单元重跑，避免一个槽内混用两种运输。

复用不是只拷贝六个结果文件。冻结包预存 54 件父证据（M1/M2 的 16 份 prompt、
16 份 raw、16 份 transport 和 6 份 canonical）的联合哈希。`prepare` 会逐单元核验
prompt/raw/transport 链，重新取回原文并展开，机械复算六份 canonical 后才复制。
